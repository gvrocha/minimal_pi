# Lessons learned — Alpine headless flashing

Distilled from a real flash session on `mobile_aprs_gateway` (2026-07-04), attempting exactly the procedure in `flashing-base-alpine.md`. Keeping the operational lessons here even though **that session ended without a confirmed successful headless boot on a fresh card** — the open question at the end is exactly the next thing to resolve, not a solved problem being written up after the fact.

**Update (2026-08-01, `minimal_pi`):** the full eth0 (direct-cable static IP) milestone-1 path is confirmed working **end-to-end on real hardware (Pi 3B+)**: blank SD card → flat-layout boot → apkovl-driven first-boot SSH → fully CLI-automated `setup-alpine` disk install (`yes | setup-alpine -e -f answerfile`, no interactive session anywhere) → reboot into a persistent, disk-booted (`/dev/mmcblk0p2 ext4` root), SSH-accessible Alpine 3.21.6 system. Zero internet access needed at flash-time on either machine, backed by a from-scratch offline package-vendoring + signing setup (`apks-extra/`) for the handful of packages Alpine's own RPi tarball doesn't ship locally. Four real bugs found and fixed along the way (see "Fixed bugs" below), plus a still-open hardware-reliability question (Ethernet link flapping under I/O load — see "Hardware reliability") that turned out not to block the automation once long-running installs run detached from the live SSH session.

**Update 2 (2026-08-01, same day):** milestone 1 was re-scoped to require a single driver script, not just proven manual steps — see STATUS.md. `flash-and-install.sh` now does exactly that, confirmed end-to-end on real hardware (hostname `minpi`) after finding and fixing two more real bugs — see "`flash-and-install.sh` — single-script milestone-1 driver" below. **Milestone 1 is done.** WiFi AP mode is now milestone 2, not part of milestone 1 — still not started beyond vendoring/installing `hostapd`/`dnsmasq` on the test device.

## Confirmed / solid

- **One aarch64 tarball covers Pi 2 (v1.2+), 3, Zero 2 W, CM3, 4/400/CM4, and 5/500/CM5.** Verified by listing the DTBs actually shipped inside `alpine-rpi-3.21.6-aarch64.tar.gz` — no per-model download needed within that family.
- **Card size matters a lot for iteration speed.** Erasing/formatting a 128GB card took **7m43s** for the `eraseDisk` step alone (FAT32 format time scales with capacity — more clusters/FAT entries to initialize). Actual usage is ~100MB of Alpine boot files + a <1KB apkovl, so an 8–16GB card is plenty and cuts iteration time dramatically if you're re-flashing repeatedly while debugging.
- **A direct machine↔Pi Ethernet link has no DHCP server** — plain DHCP in the apkovl won't get an address at all on that topology. Bake in a static IP on both ends instead (see `flashing-base-alpine.md` step 4). The `169.254.0.0/16` link-local range is a reasonable default since it needs no coordination with any other network.
- **macOS auto-recreates `.fseventsd`/`.Spotlight-V100`** on every mount of the FAT32 boot partition. Harmless in practice, but if you want a truly vanilla card for isolation testing, `.fseventsd` deletes with a plain `rm -rf`; `.Spotlight-V100` resists even `mdutil -i off` / `mdutil -X` and needs `sudo rm -rf`.
- **Always eject properly (`diskutil eject`) before pulling the card.** An improper pull was one of several hypotheses chased down during debugging (ruled out via `fsck_msdos` clean check, but not worth risking again).
- **A small FAT32 partition + explicit "Free Space" filler avoids the slow full-card format**, and works just as well as formatting the whole card. FAT32 format time scales with the size of the partition being formatted, not the physical card capacity — `diskutil eraseDisk` formats the whole disk as one partition, but `diskutil partitionDisk <disk> MBR "MS-DOS FAT32" BOOT 1G "Free Space" EMPTY R` creates a 1GB boot partition (format takes seconds) and leaves the rest of a 128GB card as an explicit unformatted gap. `setup-disk -m sys` repartitions the *entire physical disk* later anyway during real install, so the leftover space isn't wasted or orphaned — this is safe to use for a real deployment, not just iteration speed during debugging.
- **Raspberry Pi's ACT LED flash codes are a real, useful diagnostic** when you have no console access. Confirmed via two independent sources (official RPi docs summary + forum threads): **7 flashes = kernel image not found**. This is exactly what a vanilla-tarball boot showed when `config.txt` pointed at the nested `boot/vmlinuz-rpi` path (see "Confirmed" item below) — the flash code alone was enough to diagnose the failure with zero guesswork, no monitor/serial needed.
- **A direct-cable static-IP link can silently hijack your Mac's default route.** If the Ethernet service used for the direct link is manually configured with itself as its own "router" (e.g. `169.254.100.2` routing via `169.254.100.2`) and outranks Wi-Fi in `networksetup -listnetworkserviceorder`, macOS may prefer it for the *default* route the moment it's active — breaking all normal internet access on the Mac for the duration, with no obvious symptom beyond "the internet stopped working." Fix: `sudo networksetup -ordernetworkservices "Wi-Fi" ...(rest in original order)...` to put normal networking back above the point-to-point link. Worth checking `route -n get default` any time you bring up a direct-cable link like this.

## Confirmed — the boot-layout question is resolved (for Pi 3B+)

Both open suspects from the original `mobile_aprs_gateway` session are now resolved or superseded, via a real vanilla-tarball test on a Pi 3B+ (2026-08-01):

1. **Boot partition file layout — CONFIRMED, flat layout is required on Pi 3B+.** A raw, zero-customization tarball extract (kernel/initramfs nested under `boot/`, matching the tarball's own `config.txt`) produced the 7-flash "kernel not found" LED code — no Ethernet light, no other sign of life. Flattening the layout (`mv /Volumes/BOOT/boot/* /Volumes/BOOT/`, `config.txt` → `kernel=vmlinuz-rpi` / `initramfs initramfs-rpi`) with *zero other changes* fixed it: the 7-flash code disappeared and an Ethernet link came up. This is empirically confirmed for **Pi 3B+ only**. The tarball and `config.txt` are shared across the whole aarch64 Pi family, but the actual boot-chain binary differs by generation (Pi 1/2/3/Zero use `start.elf`, Pi 4 uses `start4.elf`, Pi 5 uses a materially different bootloader/EEPROM scheme) — official Pi docs say subdirectory kernel paths are firmware-wide supported, and this is a real case where that didn't hold on this board. Don't assume this generalizes to Pi 4/5 without testing those directly.
2. **DHCP-round-trip timing question — superseded, not directly tested.** Both real tests so far used the static-IP direct-cable path, which sidesteps the question entirely (no DHCP wait either way). Still genuinely open for the DHCP/same-LAN case if anyone picks that up.

## Fixed bugs in `build-apkovl.sh` (found 2026-08-01, all three now fixed in the script)

Getting from "vanilla tarball boots" to "first-boot SSH actually works" surfaced three separate, unrelated bugs — each one produced a *clean, misleading* failure symptom with no indication of the real cause:

1. **Relative `OUTDIR` silently discarded the output.** The final step was `( cd "$WORKDIR" && tar czf "$OUTFILE" etc root )` — but `$OUTFILE` was built as `"$OUTDIR/localhost.apkovl.tar.gz"` *before* that `cd`. If `$OUTDIR` was a relative path (e.g. `.`), it resolved against `$WORKDIR` *after* the `cd`, so the tarball got written inside the temp dir and then deleted by the `trap 'rm -rf "$WORKDIR"' EXIT` on exit. The script printed its normal success message and exited 0 — the caller has no way to know the output vanished short of checking the destination file's mtime. Fix: resolve `OUTDIR` to an absolute path (`OUTDIR=$(cd "$OUTDIR" && pwd)`) immediately after validating it, before `$WORKDIR` ever exists. **Always pass an absolute path as the output-dir argument until this fix is confirmed elsewhere**, and don't trust a "Wrote ..." message alone — check the file's timestamp.
2. **Enabling the sshd runlevel symlink doesn't install the package.** The script did `ln -sf /etc/init.d/sshd etc/runlevels/default/sshd`, but never told Alpine's diskless-boot init to actually install `openssh-server` — so `/etc/init.d/sshd` didn't exist yet and the symlink was dangling. Symptom: Ethernet comes up fine, `ping` works, but `ssh` gets a clean **connection refused** (TCP stack is up, nothing bound to port 22) — nothing about this points at "the wrong package list." Root cause, confirmed by reading `mkinitfs`'s `initramfs-init.in` directly: the diskless-boot init only installs packages listed in the apkovl's `etc/apk/world`, then runs `apk add --root $sysroot ... $pkgs` against the local `apks/` repo already on the boot partition (which does ship a full `APKINDEX.tar.gz`, confirmed present). Fix: apkovl now writes `etc/apk/world` containing `openssh-server`. `openssh-server` alone is enough — its `install_if = openrc openssh-server-common=<ver>` metadata makes `apk`'s solver automatically pull in `openssh-server-common-openrc` (the package that actually owns `/etc/init.d/sshd`) once `openrc` (always present) and `openssh-server-common` (a normal dependency of `openssh-server`) are both satisfied. No need for the full `openssh` meta-package — sshd doesn't need the ssh client.
3. **Apkovl tarball wasn't root-owned.** `build-apkovl.sh` runs as a regular Mac user, and plain `tar czf` embeds the *creating* user's numeric UID/GID into the archive. Unpacked as root on the Pi during boot, that numeric ownership is preserved verbatim — so `/root/.ssh/authorized_keys` ended up owned by a non-root UID. Symptom: still a clean SSH rejection, but this time a proper one — `Permission denied (publickey,password,keyboard-interactive)`, with the *correct* key fingerprint and *correct* `700`/`600` permission bits on inspection. sshd's `StrictModes` (on by default) silently rejects a key file that isn't owned by the connecting user, with nothing surfaced to the client to explain why. Fix: `tar czf ... --uid 0 --gid 0 --uname root --gname root etc root` forces root ownership into the archive regardless of who's running the script. (macOS ships `bsdtar`/libarchive, which supports these flags directly — confirmed via `man tar`.)

**Debugging note for next time:** all three of these produced *different* symptoms (silent no-op, connection refused, clean permission denied) for what looked from the outside like "the same kind of failure" (can't get an SSH session). Don't assume a single root cause once one fix doesn't fully resolve things — verify each layer (file actually written → package actually installed → ownership actually correct) independently rather than guessing at the next most-likely single cause.

4. **A fourth bug, found later while validating `setup-alpine`: no `modloop` service, ever.** mkinitfs's diskless-boot init only adds its own standard baseline services (`devfs`, `dmesg`, `mdev`, `hwdrivers`, `modloop` in `sysinit`; `modules`, `sysctl`, `hostname`, `bootmisc`, `syslog` in `boot`; clean shutdown handling) when the apkovl either doesn't exist or contains an empty marker file, `etc/.default_boot_services` (existence-only check, content ignored; mkinitfs removes it after acting on it, so nothing lingers on the persistent install). A from-scratch minimal apkovl like this one's has neither by default. Symptom: everything *looks* fine (`rc-status` shows `networking`/`sshd` started, no errors at boot) but `/lib/modules` never gets populated and `setup-alpine`'s disk-install step fails outright with `mountpoint: /.modloop: No such file or directory`. Fix: `touch etc/.default_boot_services` in the apkovl.

## `setup-alpine` (step 6) full CLI automation — research notes (2026-08-01)

`setup-alpine` supports non-interactive use via `-f <answerfile>` (a shell-sourced file of `*OPTS` variables) plus `-e` (empty root password, skips the one prompt the answerfile can't cover). Read `setup-alpine.in`, `setup-user.in`, `setup-sshd.in`, `setup-disk.in`, and `libalpine.sh.in` directly (all in the `alpine-conf` gitlab repo) to nail down exactly what's needed for a *fully* non-interactive run — several of the defaults are real footguns:

- **`-q` (quick mode) is incompatible with a full install** — it sets `empty_root_password=1` and a couple of other conveniences, but the script `exit 0`s right after the APK-mirror step, **before** the User/sshd/Disk-install sections ever run. Use `-e` alone, not `-q`, and make every step non-interactive via the answerfile instead.
- **`USEROPTS` needs to be explicitly `"none"`.** If unset, `setup-alpine` falls back to `${USEROPTS:--a -g 'audio input video netdev'}` — flags with no username, which makes `setup-user` interactively prompt for one. `USEROPTS="none"` (alone, no other flags) is specifically special-cased in `setup-user` to skip cleanly. Matches this repo's root-only philosophy anyway — no extra user needed for milestone 1.
- **`INTERFACESOPTS="none"` is the right call when eth0 is already configured by the apkovl** — it leaves the current, already-working interface config alone. Re-running `setup-interfaces` against a live directly-cabled SSH session risks disrupting the very connection you're running the command over.
- **`DNSOPTS` needs an explicit domain *and* nameserver(s), even on a static-IP link with no real DNS**, e.g. `DNSOPTS="-d lan 1.1.1.1 8.8.8.8"` — `setup-dns` is only skipped entirely when `/etc/network/interfaces` already has a `dhcp` line; otherwise it always runs, and with no args it prompts interactively for both domain and nameserver.
- **`setup-sshd` doesn't touch an apkovl-provided `authorized_keys`** as long as `ROOTSSHKEY` (its `-k` flag) is left unset — it only appends a key if one is explicitly passed. It does re-run `apk add openssh` (harmless no-op if already installed) and may enter its "ask about root login" branch, but that branch is itself gated on an `$interactive` flag that's only set when no ssh-server choice was given on the command line — passing `SSHDOPTS="openssh"` directly avoids it, so no prompt actually fires.
- **`setup-disk`'s erase confirmation is unconditional and can't be bypassed by any flag** — `confirm_erase()` always calls `ask_yesno "WARNING: Erase the above disk(s) and continue? (y/n)" n`. It reads via a plain `read -r resp` (confirmed in `libalpine.sh.in`), so it accepts piped stdin fine — no real TTY needed. Use `yes | setup-alpine -e -f answerfile`, not `echo y | ...`: there are multiple `ask_yesno` call sites in `setup-disk.in` depending on code path, and only one is guaranteed to fire for a straightforward `-m sys` install — `yes` keeps answering until the pipe closes, `echo y`'s single answer risks a hang on any unexpected second prompt.
- **`setup-disk` needs the local apk repo(s) to survive its own unmount of the boot media.** When `-m sys /dev/mmcblk0` targets the *same disk* the diskless boot is running from, `setup-disk` has to unmount that media to repartition it — but Alpine's own local package cache (`apks/`) lives on that same media, so the repo vanishes mid-install unless copied into tmpfs first. This is what `offline-install-prep.sh` does, and it has to run *before* `setup-alpine`. Don't try to unmount the boot media yourself as a "cleanup" step afterward, though — see the `modloop`-pins-the-mount note in "Offline package vendoring" below.
- **Run it detached (`nohup ... &`), not as a foreground SSH command.** A live SSH session running the install directly turned out to be fragile against the Ethernet link flapping mid-install (see "Hardware reliability" below) — the *SSH session* dying doesn't mean the underlying process died, but a plain foreground `ssh ... "yes | setup-alpine ..."` ties the two together for no reason. `ssh ... "nohup sh -c 'yes | setup-alpine -e -f answerfile' > install.log 2>&1 < /dev/null &"` survives a dropped link; reconnect later and poll the log / `pgrep` for completion.

**Confirmed working end-to-end (2026-08-01, Pi 3B+, wall-outlet power):** `yes | setup-alpine -e -f answerfile`, run detached per above, completed with `Installation is complete. Please reboot.` — real partitions created (300M FAT32 boot + rest as ext4 root), kernel/bootloader installed. Rebooted and verified directly: `hostname` returns the answerfile's value (not `localhost`), `mount` shows `/dev/mmcblk0p2 on / type ext4` (real persistent disk root, not tmpfs), and SSH with the original apkovl-authorized key works against the fresh host keys the persistent install generated. This is the complete milestone-1 ethernet path, done. See `build-answerfile.sh` and the updated step 6 in `flashing-base-alpine.md` for the implementation.

## Offline package vendoring — `apks-extra/` (2026-08-01)

**The stock `alpine-rpi-*-aarch64.tar.gz` does not include everything `setup-disk -m sys` needs.** Specifically missing from its local `apks/` cache: `dosfstools`, `linux-rpi` (the real kernel *package* — different from the raw `vmlinuz-rpi` file the diskless boot uses directly, and not needed until the persistent-install step), `raspberrypi-bootloader` + `raspberrypi-bootloader-common`, and their full transitive dependency closure (`mkinitfs`, `abuild` + its own build-time deps, three `linux-firmware-*` packages, etc. — 26 packages, ~49MB total). Symptom: `setup-disk` fails with `ERROR: unable to select packages: ... (no such package)`, but only for packages that genuinely don't exist anywhere in the offline repo — this isn't a bug in our scripts, Alpine's tarball just doesn't ship these.

Confirmed this is a **hard requirement for real internet access** if using the stock local repo alone — not something `--allow-untrusted` or clever local-caching can route around, since the packages are missing entirely, not just untrusted. Given this project's explicit goal of a fully offline-capable ("desert island") repo, the fix was to vendor them:

1. **Resolve the full dependency closure programmatically**, not by chasing "no such package" errors one at a time — cross-reference each target package's `D:` (depends) lines in the official `main`/`community` `APKINDEX` against what's already in the stock tarball's `apks/aarch64/`, recursively. Doing this by hand (add one missing package, rerun, discover the next missing one, repeat) burns an install cycle per package; a small script resolving the whole closure up front is much faster. Watch for **zsh's `set -- $var` not word-splitting on whitespace by default** (unlike bash/sh) if scripting this on a Mac — use `set -- ${=var}` (zsh's explicit-split syntax), or `sh -c`, or you'll get one garbled argument instead of several.
2. **Download the missing `.apk` files directly from `dl-cdn.alpinelinux.org`** (`https://dl-cdn.alpinelinux.org/alpine/v3.21/main/aarch64/<pkg>-<version>.apk`) onto the machine that has internet — no need to ever give the Pi internet access itself.
3. **Build a proper repo layout, `<repo-root>/aarch64/APKINDEX.tar.gz` + the `.apk` files** — `apk index -o APKINDEX.tar.gz --rewrite-arch aarch64 *.apk` (run on an aarch64 Alpine system — the Pi itself works, `apk-tools` is already there). **The `aarch64/` subdirectory is mandatory**: a flat layout with `APKINDEX.tar.gz` at the repo root produces a bewildering `WARNING: opening <path>: No such file or directory` from `apk update`/`apk add` that looks like a permissions or trust problem but is actually just apk looking in the wrong place (`<repo-root>/$ARCH/APKINDEX.tar.gz`, always).
4. **Sign the index — `--allow-untrusted` alone does not solve this for `setup-disk`.** apk requires a signed index to trust a repo by default. `--allow-untrusted` works for manual `apk add` commands you control, but `setup-disk`'s own *internal* `apk add --root $newroot ...` calls (in `setup-disk.in`) don't pass that flag, and you don't get to inject it — so an unsigned repo silently blocks the real disk-install step even after it works fine for ad hoc testing. Real signing is the only fix that reaches `setup-disk`'s own calls too.
   - Get `abuild-sign`/`abuild-keygen`/`abuild-tar` by extracting them directly from the downloaded `abuild-*.apk` (`tar xzf abuild-*.apk`) rather than fully `apk add`-installing the `abuild` package (which pulls a build-toolchain-shaped dependency chain: `fakeroot`, `lzip`, `patch`, `pkgconf`, etc.) — just copy `usr/bin/abuild-{sign,keygen,tar}` + `usr/share/abuild/` onto the aarch64 machine and run them directly with `ABUILD_SHAREDIR` pointed at the copied share dir.
   - `abuild-keygen`-equivalent: `openssl genrsa -out key.rsa 4096 && openssl rsa -in key.rsa -pubout -out key.rsa.pub`.
   - `abuild-sign`'s own signing recipe (`do_sign()` in the script) is: `openssl dgst -sha256 -sign key.rsa -out .SIGN.RSA256.<pubkey-basename> APKINDEX.tar.gz`, then tar+gzip *just that signature file* and prepend it to the original index (`cat sig.tar.gz APKINDEX.tar.gz > signed.tar.gz` — gzip transparently supports concatenated multi-member streams, so this produces one valid file apk reads as two members).
   - **`abuild-sign`'s own `tar --owner=0 --group=0 ...` call uses GNU-tar long-option syntax that busybox `tar` (what's on the Pi) doesn't support** — it fails with a "unrecognized option" usage dump that gets silently piped through the rest of the pipeline as garbage "data," producing a corrupt-but-not-obviously-wrong signature (file size barely changes, the tool still prints "Signed"). Don't trust exit code 0 alone here — check the *content* (`tar tzvf` should show both a `.SIGN.*` member and the original `APKINDEX` member; a real RSA-4096 signature is ~512 bytes). Fix: since you're already running as root when creating the sig file (so it's already owned 0:0), busybox tar's `--numeric-owner` (which *is* supported) is sufficient — drop the GNU-only `--owner`/`--group` flags entirely and run the tar step manually rather than trusting `abuild-sign`'s own invocation on a busybox host.
   - Install the public key into `/etc/apk/keys/` (both the live session, for ad hoc testing, and baked into every apkovl going forward via `build-apkovl.sh` — see fix #4 above) to make `apk add` trust it without `--allow-untrusted`. **`setup-disk` copies `/etc/apk/keys/*` into the newly-installed root automatically** before its own package-install step — confirmed by reading `setup-disk.in` — so a key trusted on the diskless session is trusted on the persistent install too, with no extra propagation step needed.
5. **Ship `apks-extra/` on the SD card's boot partition itself, not via `scp`.** For genuine offline/"desert island" self-sufficiency, the supplemental repo needs to be reachable without the Mac ever touching the Pi over the network — copy it onto the FAT32 boot partition during flashing (alongside Alpine's own `apks/`), same as the vanilla tarball. `offline-install-prep.sh` (baked into every apkovl, alongside `apks-cache`'s copy-to-tmpfs step) copies *both* `apks/` and `apks-extra/` into tmpfs and configures `/etc/apk/repositories` before `setup-alpine` ever runs — the only network dependency left anywhere in the flow is the original one-time `git clone` of this repo plus the original Alpine tarball download, both done in advance while there's still internet.
   - **Don't try to `umount` the boot media as a "cleanup" step after copying** — `/.modloop` (kernel modules) is loop-mounted from a file on that same partition (once fix #4 above is in place and modloop actually mounts, which it should), so the unmount fails with `Resource busy`. This is fine — leave it mounted; `setup-disk` has its own correct handling for this exact situation via a helper called `copy-modloop` (copies the modules out of the loop mount, stops the `modloop` service to release it, *then* unmounts) — it runs automatically at the right point in `setup-disk`'s own flow, no need to preempt it.
6. **The private signing key must never go in the repo.** It's in `apks-extra/README.md` — not duplicated here since that's the file someone will actually go looking at when they need to re-sign the index.

**Known gap, confirmed on a real installed device:** `/etc/apk/repositories` on the resulting persistent system is non-functional — both lines present but commented out, still pointing at the tmpfs paths (`/root/apks-cache`, `/root/apks-extra`) used transiently during the offline install, which don't exist post-reboot. This is a direct consequence of `APKREPOSOPTS="-1"` failing silently (no internet during the answerfile-driven install — see the `setup-alpine` automation section above): the running diskless system's own `/etc/apk/repositories` never got pointed at a real mirror, and `setup-disk` carries that same (now-stale) config into the new root. `apk add anything` won't work on the deployed device out of the box, even once it has real internet in the field — a downstream provisioning step needs to fix this up first (e.g. `setup-apkrepos -1`, or hand-write a `dl-cdn.alpinelinux.org` line).

## Hardware reliability — Ethernet link flapping under I/O load, USB adapter dropouts

Two separate real-hardware annoyances hit during live validation, neither fully root-caused yet:

- **The Pi 3B+'s Ethernet link (`lan78xx` — it's USB-internal on this board, not a dedicated controller) repeatedly drops and reconnects** (`dmesg`: `eth0: Link is Down` / `Link is Up`, cycling every tens of seconds to several minutes), with a rough correlation to heavy SD-card I/O (`mkfs`, package installs during `setup-disk`). Classic signature of power-supply undervoltage on this board (Pi 3B+'s onboard Ethernet shares the internal USB2 hub, so a brownout under load resets it) — **but not fully confirmed**: `dmesg` shows no explicit undervoltage flag (that surfaces via `vcgencmd`, not installed on this minimal image), and the flapping *continued even after* switching from a power bank to a wall-outlet 165W GaN charger. Worth knowing: a high wattage *rating* doesn't guarantee sufficient *sustained current* reaches the Pi — many multi-port GaN chargers require USB-PD negotiation to unlock their higher-current tiers, and the Pi 3B+ (micro-USB, no PD support) may get stuck on a low fallback current regardless of the charger's rated capacity; cable quality (thin-gauge wire, voltage drop under load) is an independent, equally common cause. **Next step if this recurs:** try the official Raspberry Pi power supply specifically, or measure actual voltage at the Pi's power input under load (a "USB power meter" inline adapter is the cheap way) rather than trusting the charger's label.
  - **Practical workaround that worked regardless of root cause: run long-haul commands (`setup-alpine`) detached (`nohup ... &`)**, not tied to the live SSH session — see the `setup-alpine` automation section above. The link flapping didn't stop, but it stopped being fatal.
- **The Mac-side USB Ethernet adapter itself (not just its IP config) intermittently disappeared entirely from `networksetup -listallhardwareports` / `ifconfig -l`** during this session — not a software/config issue, the device vanished from macOS's view of connected hardware. Reseating the USB connection fixed it each time. Unclear if related to the same power questions (unlikely, different device/power domain) or just a flaky USB port/cable on the Mac side. Also separately: **toggling macOS Internet Sharing on a manually-configured static-IP interface can leave it in a stuck no-IP state that even reapplying the static config doesn't fix** — a physical unplug/replug of the adapter was what actually cleared it, `networksetup`/`ifconfig` commands alone did not.
- **A direct-cable static-IP link can silently hijack your Mac's default route** if the point-to-point service outranks Wi-Fi in service order — see the entry in "Confirmed / solid" above. Worth rechecking `route -n get default` any time Internet Sharing or a service-order change happens, not just once at the start of a session.

## `flash-and-install.sh` — single-script milestone-1 driver (2026-08-01)

Milestone 1 was re-scoped mid-project: proving the individual steps work isn't "done" — a single script has to take a blank card to a headless SSH-accessible persistent install in one call (confirmed directly with the user, not assumed). `flash-and-install.sh` is that script, and it's now been run successfully end-to-end against real Pi 3B+ hardware (hostname `minpi`, 125GB card) — but not on the first try. Two real bugs surfaced during that live run, both fixed:

1. **Must be invoked with `bash`, not `sh`.** The script uses bash arrays and process substitution (`<(...)`) for the network-service-reorder logic (see "Confirmed / solid" below), but its own usage text originally said `sh flash-and-install.sh ...` — matching this repo's convention for every *other* script here, all of which are genuinely POSIX `sh`. macOS's `/bin/sh` is bash running in a restricted POSIX-compatibility mode that rejects both features with a plain syntax error. Caught only by actually running it (`bash -n` on the file passes fine — that validates bash's own grammar, not what happens when the same file is fed to `sh`). Fixed by correcting the usage docs to say `bash` explicitly, with a comment explaining why. **If extending this script, verify with `sh -n` too, not just `bash -n` — they parse differently and only one matches how the docs tell people to invoke it.**
2. **The final sanity-check queries (hostname, root mount) had no error tolerance and crashed the script one step from the finish line.** The wait-for-SSH-after-reboot loop is properly retry-tolerant, but it succeeded on its very *first* check in the real run (zero dots printed) — and the very next command, a bare `GOT_HOSTNAME=$(ssh ... hostname)` with no `2>/dev/null` and no fallback, hit a brief "Connection refused" moments later (sshd flickering while first-boot setup — fresh host key generation, openrc's default runlevel — finished settling) and took the whole script down via `set -e`, *after* the actual disk install had already fully succeeded. Confirmed via direct `nc -zv`/`ping` checks run independently at the time: the Pi was already back up and stable within seconds: the failure was a race, not a real problem. Fixed with a small retry-with-fallback wrapper (`ssh_output_retry`) around just those two purely-informational queries, so a late transient blip can no longer discard a successful run. **General lesson: anything after the "real work" is done (the disk install completing) should degrade to a warning, never a hard exit — the whole point of getting that far is that failure past that point isn't actually failure.**
   - **Follow-up (same day, next test run): the original 30-second retry budget on `ssh_output_retry` still wasn't generous enough.** A subsequent run showed `GOT_HOSTNAME` give up and print the placeholder while `GOT_ROOT` — same function, same options, tried ~30s later — succeeded fine. Not a host-key or connectivity issue (host-key pinning was already off entirely by this point, see below): the persistent boot's wait loop had succeeded on its first check, likely catching the tail end of the dying pre-reboot session rather than the genuinely-ready new one, and the real persistent system (fresh host keys, full service startup) needed more than 30 more seconds to finish settling. Bumped the retry budget from 10×3s to 40×3s (~2 minutes) — still bounded, still just degrades to the placeholder rather than failing, but generous enough that this specific race is very unlikely to still bite.

3. **`StrictHostKeyChecking=accept-new` doesn't help on a second re-flash to the same static IP — and this workflow always reuses the same IP.** A follow-up test run (adding the optional secondary-pubkey argument) hit this directly: the script's wait loop spun for the full 5-minute timeout ("Never reached root@... over SSH") even though the Pi was up and answering fine — manually running `ssh root@169.254.100.1` surfaced the real cause immediately: "REMOTE HOST IDENTIFICATION HAS CHANGED." `accept-new` only auto-trusts a host with *no* existing `known_hosts` entry; it does not override a *changed* key for a host already seen. Every fresh Alpine boot generates a new random host key, and `169.254.100.1` is a rotating identity by design here (whatever card is currently flashed and plugged in) — so the *previous* run's cached key in `known_hosts` reliably conflicts with the *next* run's, on every single re-flash. Purging the stale entry (`ssh-keygen -R`) would only defer the same conflict to the next run. Fixed properly instead: every ssh/scp call the script makes now uses `-o UserKnownHostsFile=/dev/null -o StrictHostKeyChecking=no` (bundled in a shared `SSH_OPTS` array) — host-identity pinning is the wrong model entirely for a host whose identity is expected to change every run. This only affects the script's own internal automation; a human's own manual `ssh root@<pi-ip>` afterward still uses their real `known_hosts` and behaves normally. **General lesson: the same "verify don't assume" instinct that caught the previous two bugs applies to diagnostics too — the user's own manual `ssh` attempt, not any log inside the script, is what actually surfaced the real cause here. When a wait-loop times out, trying the underlying command by hand is the fastest way to find out whether it's a real timeout or a misleadingly-similar-looking different failure.**

Multi-user detail worth keeping in mind if this comes up again: the Mac running this script needs sudo (for `diskutil partitionDisk` and `networksetup -setmanual`), but the `<pubkey-file>` argument is unrelated to that — it only controls what's authorized on the *Pi's* side. The script's own automatic `ssh`/`scp` calls to the Pi authenticate using whatever default SSH identity belongs to *whichever user's shell actually runs the script*, not whatever path is passed as that argument. On a Mac where the sudoer account (e.g. a dedicated admin user) is different from the account whose key you actually want authorized long-term, run the script as the sudoer using *that user's own* keypair, then append the other user's pubkey to `/root/.ssh/authorized_keys` as a one-line follow-up afterward — trying to thread one user's private key through another user's session is both harder and a needless security wrinkle, since the two concerns (local sudo rights, remote SSH identity) don't actually need to be the same user at all.
