## Milestone 1 — Pi 3B+ headless SSH via Ethernet, single script

**Re-scoped 2026-08-01** (was "Ethernet OR AP" — split into two milestones so Ethernet can be called done on its own merits, with WiFi AP as a separate follow-on milestone rather than blocking this one).

Done when a single script (or, if needed, a matched pair — one run on the laptop to build the SD card, one run on the Pi) takes a blank SD card to a headless, SSH-accessible, persistent Alpine install over Ethernet, with no other manual steps.

- [x] **Steps individually proven — done as of 2026-08-01.** Blank SD card → headless first-boot SSH (apkovl) → fully CLI-automated `setup-alpine` disk install → persistent, disk-booted, SSH-accessible Alpine 3.21.6 system. Zero interactive steps, zero internet access needed at flash-time on either machine. Confirmed on real Pi 3B+ hardware, direct-cable static-IP topology.
- [x] **Single script — confirmed working end-to-end as of 2026-08-01.** `alpine/flash-and-install.sh` collapses all of `flashing-base-alpine.md`'s steps into one Mac-side call (must be run with `bash`, not `sh` — see script header): partitions the card, extracts the tarball, flattens `boot/`, copies `apks-extra/`, builds the apkovl, ejects, configures the Mac's own interface (with an automatic fix for the documented default-route-hijack gotcha), waits for the Pi over SSH, and drives `offline-install-prep.sh` → `build-answerfile.sh` → detached `setup-alpine` → reboot, retrying through the documented Ethernet-link-flapping issue at every remote step. Run end-to-end against real Pi 3B+ hardware (hostname `minpi`, 125GB card) — three real bugs found and fixed along the way across that run and a follow-up (adding an optional secondary-pubkey argument), including a host-key-pinning issue that would have hit every subsequent re-flash to the same static IP (see `lessons-learned.md`). **Milestone 1 is done.**

## Milestone 2 — Add WiFi AP option, single script

Same bar as milestone 1 (one script, or laptop+Pi pair), extended so the Pi can host its own WiFi access point for headless SSH access when no Ethernet is available — no separate router/switch needed.

- [x] **AP config — hostapd.conf/dnsmasq.conf design done as of 2026-08-02.** `hostapd`, `dnsmasq`, `dnsmasq-common` resolved, vendored into `apks-extra/`, and installed successfully on the live test Pi (2026-08-01) — a real signing-process bug was found and fixed along the way (see `lessons-learned.md`). `alpine/wifi-ap/hostapd.conf` and `alpine/wifi-ap/dnsmasq.conf` now exist: 2.4GHz (channel 6, chosen over the sibling project's untested 5GHz/DFS-exposed channel 36 for compatibility), placeholder SSID/passphrase, no NAT/forwarding/DNS-relay options since this milestone has no internet uplink — a client just gets a DHCP lease on `192.168.4.0/24` and reaches the Pi directly by IP over SSH. `wlan0` itself will need a static `192.168.4.1/24` assignment (outside the DHCP pool) wired into `build-apkovl.sh`'s `/etc/network/interfaces`, next. Config files are unverified against a real hostapd/dnsmasq binary (none available on the Mac) — syntax was hand-checked, not dry-run tested. See sibling `mobile_aprs_gateway` project for a Pi 5 precedent (never fully debugged, its own AP-mode client-association step was left unresolved) and a real Alpine nftables gotcha (not needed for this milestone's no-NAT scope, but worth knowing: `/etc/nftables.nft`, not `.conf`, is what Alpine loads at boot).
- [x] **Package vendoring — closed as of 2026-08-02.** `hostapd-openrc-2.11-r1.apk`/`dnsmasq-openrc-2.90-r3.apk` were also needed (Alpine splits OpenRC init scripts into `-openrc` subpackages, like `openssh-server`) and hadn't been vendored — added, and `apks-extra/aarch64/APKINDEX.tar.gz` regenerated + re-signed, fixing a real bug in the signing process along the way (the signature tar member needs no EOF blocks — see `lessons-learned.md`). Verified live on `minpi`: the re-signed index is trusted, and `hostapd`+`dnsmasq`+`dnsmasq-common`+both `-openrc` packages install cleanly fully offline (stock tarball's `apks-cache` covers `libnl3`/`openssl`, nothing else missing). Also confirmed both init scripts already declare correct `depend()` ordering (`need net` / `need localmount net`) — `build-apkovl.sh`'s existing plain `ln -sf`-into-runlevel pattern is sufficient, no custom OpenRC wiring needed next.
- [x] **Wired into `build-apkovl.sh` — done as of 2026-08-02.** Re-scoped from an alternate network-mode selector to an always-on additional interface (decided with the user): the WiFi AP is now baked into every apkovl unconditionally, alongside eth0, not chosen between. This kept `flash-and-install.sh` completely untouched — its Mac-side flow stays 100% wired Ethernet, no WiFi-join automation added to a script with real fragility history. `build-apkovl.sh` now: copies `wifi-ap/hostapd.conf` → `etc/hostapd/hostapd.conf` and `wifi-ap/dnsmasq.conf` → `etc/dnsmasq.conf` (both required, not optional); appends a `192.168.4.1/24` wlan0 stanza to `/etc/network/interfaces` unconditionally after the eth0 block; adds `hostapd`/`dnsmasq` to `etc/apk/world` (their `-openrc` subpackages and `dnsmasq-common` pull in automatically via `install_if`/hard-dependency, same mechanism as `openssh-server`); enables `hostapd`+`dnsmasq` via the existing runlevel-symlink pattern. Verified locally (no hardware needed for this step): both DHCP and static-IP apkovl builds produce a correctly-structured overlay — config files present and root-owned in the archive, both `eth0`+`wlan0` interface stanzas present, `etc/apk/world` and all four runlevel symlinks correct, `sh -n`/`bash -n` clean.
- [ ] **Live end-to-end AP test on real Pi 3B+ hardware** — flash a card, confirm the resulting device broadcasts the AP and a client (no Ethernet involved) can join and SSH in. Two things genuinely unverified, not formalities: whether the apkovl-provided `hostapd.conf`/`dnsmasq.conf` survive `apk add hostapd dnsmasq` without being overwritten by those packages' own shipped stub configs at the same paths (strong precedent this works, since `/etc/network/interfaces` already goes through the identical sequence — but not yet directly confirmed for these two files), and real brcmfmac AP-mode client-association behavior (the sibling project's own attempt was never confirmed working).

## Confirmed working

- Alpine headless flashing procedure (`alpine/flashing-base-alpine.md`), Pi 3B+, aarch64 tarball, direct-cable static IP.
- `build-apkovl.sh` — first-boot SSH overlay, 4 real bugs found and fixed.
- `build-answerfile.sh` + `offline-install-prep.sh` — full CLI automation of `setup-alpine`'s disk install, no internet needed (backed by vendored `apks-extra/` local repo, self-signed).

## Known gaps

- **`/etc/apk/repositories` ships with both lines commented out on the resulting installed system, but — correction, 2026-08-01 — the paths they point at (`/root/apks-cache`, `/root/apks-extra`) do survive post-reboot.** Earlier text here claimed these were transient tmpfs paths that vanish after reboot; that was wrong. Confirmed directly on a real persistent installed device: `setup-disk` carries `/root` (including these two directories) onto the real ext4 root, and simply uncommenting the two lines makes `apk update`/`apk add` work immediately against the local repos, no internet needed. The real remaining gap is just that they ship commented-out by default and never point at a real internet mirror — a downstream provisioning step (or the milestone-1/2 driver script itself) should either uncomment these local paths, or run `setup-apkrepos -1` / hand-write a `dl-cdn.alpinelinux.org` line, before assuming `apk add` works for anything beyond what's already vendored.
